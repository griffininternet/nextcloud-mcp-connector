# Phase 4: UI Design Contract

> Visual and interaction contract for the browser facing surface of the per user management
> phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This contract is a delta, not a restart.** `03-UI-SPEC.md` is the baseline and stays in
force word for word: the platform constraints, the response headers, the spacing scale, the
type scale, the palette, the accessibility rules and the copy rules below repeat it only
where phase 4 adds something. Nothing here overrides anything there (D-45). Where a section
says "unchanged", the phase 3 table is the contract.

**Scope of this contract:** three surfaces.

1. **Connections page**, one page of this ExApp: the list of connected clients of the signed
   in user, with a disconnect action per row (ROADMAP SC 2, EXAPP-02). The page already has a
   name in the shipped documentation: `docs/client-setup.md` line 339 and
   `docs/oauth-setup.md` line 572 both promise "the app's own connections page", so the page
   is called **Connections** and lives at `/connections`.
2. **The on/off switch**, rendered by Nextcloud through Declarative Settings, not by us
   (D-44). We own its copy and its placement, Nextcloud owns its pixels.
3. **The refusal when access is switched off** (D-51). Not a page: a wire answer that an
   assistant app shows to its user. It gets a contract here because it is the only thing the
   user sees after flipping the switch, and because it has to be distinguishable from the
   refusal of an invalid token.

**Out of scope (do not build here):** `prepare_context` has no browser surface at all. Its
answer is model facing text and follows the `_HINT` convention of `tools/search.py` and
`errors.py`, which is a different contract and deliberately not this one. Admin surfaces for
the allowlist and the DCR switch stay out (AUTH-07, CONTEXT deferred). An admin view of the
connections of all users stays out (CONTEXT deferred).

## Platform Constraints (inherited from phase 3, plus what this phase adds)

Everything in `03-UI-SPEC.md` "Platform Constraints" holds unchanged: server rendered HTML
from Starlette, zero JavaScript, no external asset, one nonce style block, inline SVG icons,
own neutral palette and never the Nextcloud look, sender identity on every page, English v1,
all strings in `exapp/ui/strings.py`, single column at `max-width: 560px`.

The five required response headers are unchanged and are set by `layout.page` alone:

```
Content-Security-Policy: default-src 'none'; style-src 'nonce-{nonce}'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'
X-Frame-Options: DENY
Referrer-Policy: no-referrer
Cache-Control: no-store
Content-Type: text/html; charset=utf-8
```

`no-store` is not decoration on this page either: it carries the client names and connection
dates of one named account, and the AppAPI PHP proxy caches for 3600 seconds unless told
otherwise (phase 2, pitfall 4).

What phase 4 adds:

| Constraint | Decision | Why |
|-----------|----------|-----|
| Route count | **One** new route for the user-facing part, `GET,POST ^/connections/?$`, fully anchored. Thirteen instead of twelve. A fourteenth may become necessary for the settings switch, see Open Question 1; it is not free either and needs the same justification | Every declared route is external attack surface (D-38, pitfall 14). The list, the confirm step and the disconnect are one resource, so they are one route with a named action field, exactly as `/connect` handles start and cancel |
| Access level | **PUBLIC**, with the identity check inside the app | `access_level USER` is refused here for the measured CR-01 reason: HaRP answers an anonymous request itself and records it in a per route blacklist, and the tenth refusal in 300 seconds bans the caller from the WHOLE ExApp with 502. A settings page reached from a stale tab or an expired session produces exactly those refusals as normal operation. HaRP resolves the account on a PUBLIC route too and writes it into `AUTHORIZATION-APP-API`, empty when there is none, which is what the page reads |
| Ownership check | A row may be shown and disconnected only when `authorizations.nc_user` equals the account HaRP resolved. Never the flow id, never a value from the request | The connection handle is guessable enough to be worth forging, and the account behind the browser is the only thing that answers "whose connection is this" |
| State change | Only through `POST`. Two steps: confirm, then disconnect. No `GET` disconnects anything | The phase 3 rule (T-03-35) and the reason a link cannot be a destructive action |
| Anti forgery | Hidden field, an HMAC of the connection handle under the installation data key, the same primitive as `CONFIRM_PARAM` of the consent form (T-03-50) | Needs no migration, survives a restart and a second worker, and no foreign origin can produce it |
| Settings switch storage | **Resolved 2026-08-17, the fallback row below became the design.** The assumption that `external` means "pushed to this app" was measured false: AppAPI forces `external` and stores the value itself, and no call ever reaches the ExApp (04-RESEARCH.md) | D-47 forbids a second Nextcloud roundtrip per MCP request and D-48 forbids a cache that delays the effect; a value this app cannot observe satisfies neither |
| Fallback if `external` is unavailable → **now the design** | The switch does **not** fall back to a poll. It lives on `/connections` next to the list (see "The Nextcloud Settings Entry" section), and Nextcloud's settings section carries a link-only entry (`fields: []`, measured working). D-44 asked for the switch to be findable where Nextcloud shows its app switches; that is a preference, while D-47 and D-48 are measured constraints, and the constraint wins | A poll would break the one measured number this phase is not allowed to worsen (SC 5 of phase 3, one Nextcloud roundtrip per MCP call), and a delayed effect would break SC 1. Losing the second entry point costs discoverability and nothing else |
| Relationship to the old architecture draft | This table supersedes `.planning/research/ARCHITECTURE.md` lines 63 and 174, which still describe the earlier idea: the flag in `preferences_ex`, read from Nextcloud on every request. That is precisely the roundtrip D-47 forbids | The draft predates the SC 5 measurement of phase 3. Naming it here keeps the planner from implementing the older, cheaper looking sketch |
| Settings rendering | Nextcloud renders the switch in its own design system. We supply `title`, `description`, `label`, `default` and `doc_url` and nothing else | This is the one surface of this app that must look like Nextcloud, because it is Nextcloud. Our own pages must never look like it (phase 3, T-03-23) |
| New dependency | None. No template engine, no CSS framework, no icon package, no JavaScript | Unchanged from phase 3 |

## Design System

| Property | Value |
|----------|-------|
| Tool | none (no `package.json`, no `components.json`, no React/Next/Vite in this repo) |
| Preset | not applicable |
| Component library | none. Hand written semantic HTML plus the one shared CSS block of `exapp/ui/layout.py` |
| Icon library | none. The **same three** inline SVG constants of `ui/icons.py` (warning, check, cross). Phase 4 adds **no fourth icon** |
| Font | Unchanged: `system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif`; `ui-monospace, SFMono-Regular, "Cascadia Mono", Consolas, monospace` for client ids |

No fourth icon on purpose. A plug, a power symbol or a trash can would each be a new shape
for a state that already has a word: "Access is paused" is a warning callout, a finished
disconnect is a check, a refusal is a cross. An icon that appears once is an icon nobody
learns.

## Typography

Unchanged from `03-UI-SPEC.md`:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.5 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Rules that phase 4 has to apply to a list of rows:

- Exactly these four sizes, exactly two weights (400, 600). No 300, no 700, no italics.
- The app name of a connection row is **Body size at weight 600**, not a heading. It is data,
  not a section, and a page whose heading outline is a list of client names is a page a
  screen reader user has to walk through twice to find the one heading that means something.
- The client id of a row renders at 14px monospace weight 400 with `overflow-wrap: anywhere`,
  the same treatment redirect URIs get on the consent page.
- The date line of a row is the 14px muted style.
- No text below 14px anywhere, footnote included.

## Color

Unchanged from `03-UI-SPEC.md`:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F5F6F7` | Page background |
| Secondary (30%) | `#FFFFFF` | The card, the callout body |
| Accent (10%) | `#1F3A5F` | See reserved list below |
| Destructive | `#B3261E` | The heading and icon of a refusal page only |

Supporting values, all measured against their own background, unchanged: text primary
`#1A1A1A` (16.9:1 on white), text muted `#5A6270` (6.1:1 on white), border `#D5D8DD`
(decoration only, never the sole signal), warning text `#8A5A00` on warning surface `#FFF8E6`
(5.6:1), success text `#1E6B3A` on white (5.4:1).

Accent reserved for: **(1)** the primary button fill, which on this surface is exactly one
button, "Disconnect" on the confirmation page, **(2)** the focus ring on every interactive
element, **(3)** the wordmark bar rule above the card, **(4)** inline text links. Nothing
else. Never as a row background, never as a badge, never on the row level "Disconnect"
buttons of the list.

Deliberately not used: `#0082C9` and the rest of the Nextcloud brand palette, for the phase 3
reason (T-03-23). The Declarative Settings switch is the exception that proves it: it is
rendered by Nextcloud, in Nextcloud's palette, because it is Nextcloud's page.

**The destructive colour is not used on the disconnect buttons.** `#B3261E` stays reserved
for the heading and icon of a refusal, as in phase 3. A red button per row would paint a
list of ordinary, reversible actions as a list of alarms, and the user of this page came here
to disconnect something. The destructive action is marked by its label, its confirmation step
and its copy, never by hue.

Colour is never the only signal, in this phase specifically:

- "Access is paused" is a warning callout with a border, the warning icon and those literal
  words, not a tinted page;
- a finished disconnect is a success callout with the check icon and the word "Disconnected";
- the refusal at the transport level carries a named error code and a sentence, and has no
  colour at all.

## Screen Inventory

Continues the phase 3 numbering. S1 to S4 and E1 to E7 exist and are untouched.

### S5: Connections list (`GET /connections`, identity resolved, at least one connection)

| Element | Content |
|---------|---------|
| Wordmark bar | Unchanged: "MCP Connector for Nextcloud" plus the configured public host, never the `Host` header |
| Display (`h1`) | "Your connections" |
| Identity line | "You are signed in as {user} at {host}." (the phase 3 constant, reused verbatim) |
| Warning callout | Only when the switch is off. Title "Access is paused". Body: "MCP access is switched off for your account, so connected apps are refused. Nothing was disconnected." The switch block that turns it back on sits directly above (amended 2026-08-17 with the on-page switch; the old pointer sentence to Nextcloud settings is gone) |
| Section heading (`h2`) | "Connected apps" |
| Row list | One `<li>` per authorization of this user, newest first. Each row: app name (Body/600), client id (14px mono, muted), "Connected on {date}" (14px muted), and one `<form method="post">` with a secondary button "Disconnect" |
| Footnote | "Apps you connected with a credential from the onboarding page are not listed here. They appear in Nextcloud under Settings, Security, Devices and sessions." |
| Secondary action | Link with the text of `CONNECT_TITLE` to `/connect` |
| Footer | Unchanged phase 3 default: "The password prompt is always Nextcloud itself. If any other page asks you for your Nextcloud password, close it." |

**Reading order, and where the eye lands first.** This screen carries no accent colour and no
primary button on purpose: nothing here is the one thing to do, the page is a list to inspect.
The order it must read in is display, then the warning callout when it is there, then the
rows, then the footnote. Weight and position carry that order, not colour.

**Callout stacking, when both can appear at once.** A disconnect on an account whose access is
paused produces the result callout of S8 and the pause warning of S5 in the same render. Fixed
order, both as the first elements of the card and above the section heading: **result first,
pause warning second**. The result answers what the user just did, the warning describes a
standing condition. On the empty state S6, which has no section heading, the same two sit
directly under the identity line in the same order.

Content rules for a row, each of them load bearing:

- **The app name is attacker input.** It comes from a DCR registration, so it goes through
  `layout.client_name` (control characters stripped, whitespace collapsed, cut to 80
  characters) before `layout` escapes it. Same rule, same function, same reason as the
  consent page: without it a registration can name itself with three lines of fake page copy.
- **The client id is shown in full and never shortened.** It is the only thing that tells two
  rows called "Claude" apart, and a value cut in the middle hides the half that differs.
- **The connection handle (`auth_id`) never appears as visible text.** It travels in a hidden
  field and nowhere else. It is the handle of a credential; the client id is public by design.
- **No "last used" column in v1.** The only timestamp in the store that could fill it is
  `clients.last_used_at`, which belongs to a client registration and not to one user's
  authorization, so a shared registration would show one user the activity of another. A per
  authorization timestamp is a store change and belongs in the plan, not in this contract.
  Until it exists, the column stays out rather than being filled with a number that is wrong.
- **Date format: `12 August 2026`.** Day, full month name, year. No `12/08/2026`, which two
  continents read differently, no relative time ("3 days ago"), which needs a clock this page
  cannot promise, and no time of day, which is noise in a list whose unit is a connection.
  The date is computed in UTC; a connection made late in the evening can therefore show the
  next day, and that is the accepted cost of not asking the browser for a timezone.

### S7: Confirm disconnect (`POST /connections`, `action=confirm`)

| Element | Content |
|---------|---------|
| Display | "Disconnect {client}?" |
| Body | "{client} loses access to your Nextcloud immediately. Nothing in your Nextcloud is deleted or changed." |
| Body | "You can connect it again at any time from the app itself." |
| Detail list (`<dl>`) | "App name" ({client}), "Client ID" ({client_id}, monospace), "Connected on" ({date}) |
| Secondary | Button "Keep this connection" (returns to the list) |
| Primary | Button "Disconnect" (accent fill) |

Interaction rules:

- Both buttons are `<button type="submit">` of **one** `<form method="post">` to
  `/connections`, distinguished by the value of the action field. The form carries the
  connection handle and the anti forgery value as hidden fields.
- **Initial focus is the heading**, never the disconnect button, through the existing
  `focus_heading=True` of `layout.page`. The phase 3 reason applies literally: a page that
  opens with the acting button focused turns a stray Enter key into the action.
- Tab order: heading, details, keep, disconnect. The safe action is reachable first, exactly
  as deny comes before approve on the consent page.
- No checkbox, no typed confirmation, no countdown. The interstitial page **is** the friction,
  and this action is reversible by reconnecting.

### S8: Result of a disconnect (answer to `POST /connections`, `action=disconnect`)

The answer is the **full list page** (S5 or S6, whichever now applies) with a callout above
the section heading, and status **200**:

| Case | Callout | Copy |
|------|---------|------|
| Disconnected | success, check icon | Title "Disconnected". Body: "{client} no longer has access. If the app is still open, it will report that it lost its connection." |
| Nothing to disconnect (resubmitted form, handle already gone, handle not this user's) | warning, warning icon | Title "Already disconnected". Body: "That connection is not listed any more. Nothing changed." |

The answer is a page and not a `303` redirect: the same CR-03 lesson as the consent decision.
A redirect after a form submission is checked against `form-action`, and rendering the result
directly is one answer instead of two, with no state to carry between them. The cost is that
a reload resubmits the form, which is precisely why the second row of that table exists and
why it is **not** an error: a disconnect that already happened, requested again, is a page
that says so calmly.

The three cases "unknown handle", "handle of another user" and "already revoked" produce the
**same** answer. A page that distinguished them would answer, for a stranger who can guess a
handle, whether that connection exists.

### E8: Not signed in (`GET` or `POST /connections`, no Nextcloud account behind the browser)

| Field | Value |
|-------|-------|
| Heading | "Sign in to see your connections" |
| Body | "This page shows the apps connected to your own Nextcloud account. Sign in at {host} and open it again." |
| Action | none |
| HTTP | 403 |
| Icon and tone | cross, error, like every other page of the error table |

403 and not 401: a 401 from a page a browser opened invites the browser's own credential
prompt, and this surface never puts a password prompt in front of a user. No link to the

here would be exactly the phishing shape the footer of every page warns about. The host is
named in words instead.

E8 is a new row of the existing `errors.py` table, not a new mechanism. E7 stays the answer
when the store cannot be read (fail closed, D-37).

## Refusal Contract (D-51, the wire answer, not a page)

The switch blocks, it does not revoke (D-46), and it blocks every way in (D-49). What the
user sees is whatever their assistant app prints from this answer, so the answer carries the
sentence.

| ID | Trigger | HTTP | `WWW-Authenticate` | Body |
|----|---------|------|--------------------|------|
| R1 | Access switched off for this account, any connection type: OAuth bearer or AppAPI app password | **403** | **absent** | `{"error":"access_disabled","error_description":"MCP access is switched off for this Nextcloud account. The owner of the account can switch it back on in Nextcloud under Settings, Security, MCP Connector."}` |
| R2 | Invalid, unknown, expired or revoked token (phase 3, unchanged) | 401 | `Bearer error="invalid_token", error_description="Authentication required", scope="nextcloud", resource_metadata="..."` | empty |
| R3 | Broken AppAPI handshake (phase 2, unchanged) | 401 | absent | empty |

Three signals separate R1 from R2, and all three are deliberate:

1. **403, not 401.** A 401 with a challenge tells an OAuth client "your token is the problem,
   get a new one", and the client would walk the entire discovery, registration and consent
   flow again only to be refused a second time. That loop would put the sign in load of a
   whole authorization dance on Nextcloud every time a user pauses access, which is the
   opposite of the SC 5 measurement this phase must not worsen.
2. **No `WWW-Authenticate` header at all.** There is nothing to authenticate with. The
   credential is fine, the decision was the user's.
3. **A named error code, `access_disabled`, plus a sentence that names the place.** The rule
   from T-03-66 holds: the sentence names the rule and the place, and carries **no** value
   from the request. No user name, no client name, no token fragment, no internal host. It is
   a constant string with no placeholder, which is also why it can be a single constant in
   `strings.py`.

`Cache-Control: no-store` on R1, like every other answer of this package.

**Where this leaves the convention, stated rather than hidden.** RFC 6750 describes a
different shape for "the credential is valid, the decision is against you": a 403 that still
carries `WWW-Authenticate: Bearer error="insufficient_scope"`. This contract omits the header
on purpose, because there is no other scope and no other credential the client could come
back with, and because the header is what pulls a client into the rediscovery loop above. The
price is real and belongs in the plan, not in a footnote: a strict client may render only
"forbidden" and drop the body, so the sentence reaches the user only when the client passes
`error_description` through. If the plan finds a client that swallows it, the answer is not to
add the challenge back; it is to accept that this user learns the reason in the Nextcloud
settings instead.

R1 is a transport level answer from `exapp/middleware.py`, the same boundary that produces R2
and R3, because that is the one place both connection types pass (D-47, D-49). There is no
second, tool level variant of this sentence: two sources for one sentence is how the two
drift apart.

## The Nextcloud Settings Entry, and where the switch really lives (D-44, resolved 2026-08-17)

**The fallback of the constraints table is the design.** Phase research measured the
Declarative Settings contract against the AppAPI source at tag v34.0.3 and against the live
test topology (04-RESEARCH.md): AppAPI forces `storage_type: external` and stores the value
itself in `preferences_ex`, and when a user flips a field, **no call reaches the ExApp**. No
push, no webhook, no declarable route; the only way to learn the new value is an OCS
roundtrip per request or a poll, both of which D-47 and D-48 forbid. A checkbox rendered by
Nextcloud therefore cannot be the switch of this design.

What replaces it, both parts measured against the running system:

**1. The Nextcloud settings entry is link-only.** A Declarative Settings form with
`fields: []` registers (200), passes core validation, and renders in the personal
`security` section as a titled block with a description and a help icon. No fourteenth
route, `SETTINGS_PLACE` holds.

| Schema key | Value | Why |
|-----------|-------|-----|
| `section_type` | `personal` | It is the user's own entry. EXAPP-02 is per user by definition |
| `section_id` | `security` | Measured addressable for an ExApp form. Where the user already manages "Devices and sessions" |
| `title` | "MCP Connector" | The name of the app, so the user recognises it in a long settings page |
| `description` | "Assistant apps such as Claude or ChatGPT can reach your files, calendar, notes, contacts and Deck cards through this connector, exactly as far as your own account reaches. Your connected apps and the switch that pauses them are at {connections_url}." | The `doc_url` renders as a small help icon, and a help icon is easy to miss. The address is therefore also spelled out as text |
| `doc_url` | The absolute public URL of `/connections` | The only link a Declarative Settings section can render. This is the link D-44 asks for |
| `fields` | `[]` | A field whose change the app cannot observe would be a switch that silently does nothing until the next poll, which is the worst of all versions of this feature |

Registration happens in the `/enabled` lifecycle handler
(`POST /ocs/v2.php/apps/app_api/api/v1/ui/settings`, idempotent); disabling hides the entry,
uninstalling cleans it up, both on AppAPI's side (04-RESEARCH.md).

**2. The switch itself lives on `/connections` (S5 and S6), above the client list.** It is a
`<form method="post">` with a **named state as the action, `action=pause` or `action=resume`**,
never a `toggle`: a resubmitted or replayed form then re-states a state instead of flipping
it, the same idempotence that makes "Already disconnected" an answer and not an error.
(Amended 2026-08-17; the first draft said `toggle`.) Rendered as one sentence of state plus
one button, because a checkbox that needs a submit button next to it is two controls
pretending to be one:

| State | Sentence (Body, 400) | Button |
|-------|----------------------|--------|
| Access on | `SWITCH_ON_STATE` = "MCP access is on. Connected apps can use your Nextcloud." | Secondary button `SWITCH_TURN_OFF` = "Pause access" |
| Access off | `SWITCH_OFF_STATE` = "MCP access is paused. Connected apps are refused, nothing is disconnected." | **Primary** button `SWITCH_TURN_ON` = "Turn access back on" |

- Turning **off** is the secondary style on purpose: it is the emergency brake, present but
  not advertised, and the destructive red stays unused exactly as on the disconnect buttons
  (nothing is destroyed, D-46).
- Turning **on** is the one moment this page carries the accent colour: the page state is
  degraded and the primary action is the way back. This amends the S5 note "no accent on
  this page": it holds while access is on, and the paused state is the named exception.
- The toggle POST carries the same anti forgery HMAC as the disconnect forms and answers
  with the re-rendered list (CR-03 shape), where the pause callout appears or disappears as
  the proof of effect. `SETTINGS_FIELD_TITLE`, `SETTINGS_FIELD_LABEL` and
  `SETTINGS_FIELD_DESCRIPTION` from the copy table are retired with the checkbox; the four
  `SWITCH_*` constants above replace them, and `SETTINGS_FIELD_DESCRIPTION`'s sentence about
  what pausing does and does not do moves into `SWITCH_OFF_STATE` and the confirm-free flow
  (no interstitial: pausing is reversible with one click on the same page, unlike a
  disconnect, which is why the disconnect keeps its confirm step and the switch does not).
- Default state remains **on** (D-50), now enforced by our own store rather than a schema
  `default`.

The pause callout of S5/S6 ("Access is paused") remains as specified; with the switch on the
same page it stops being only a pointer to Nextcloud settings, so `CONNECTIONS_PAUSED_BODY`
drops its last sentence ("Switch it on again in Nextcloud under...") in favour of the switch
block directly above. `SETTINGS_PLACE` stays for the R1 wire answer, whose reader is not on
this page: `ACCESS_DISABLED_DESCRIPTION` now ends "...can switch it back on on the
connector's connections page, linked in Nextcloud under Settings, Security, MCP Connector."

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "Disconnect" (confirmation page, the one accent button of this surface) |
| Secondary CTA | "Disconnect" (row level, secondary fill, opens the confirmation), "Keep this connection", "Connect an assistant app" |
| Empty state heading | "No connected apps" |
| Empty state body | "No assistant app is connected to your Nextcloud through this connector. Connect one from the app itself, or use the onboarding page for an app that cannot sign in by itself." |
| Error state | Problem plus next step, never a stack trace, never an internal path, never a token or handle. E8 above, E7 unchanged for a store that cannot be read, R1 for the paused refusal |
| Destructive confirmation | **Disconnect a connection**: an interstitial page (S7) that names the app, its client id and its connection date, states the consequence ("loses access immediately") and the limit of that consequence ("Nothing in your Nextcloud is deleted or changed"), and offers "Keep this connection" before "Disconnect". Initial focus on the heading, not on the button. No checkbox and no typed name: the action is reversible by connecting again, and friction that outweighs the risk teaches people to click through it |

Copy rules, inherited from phase 3 and enforced by the checker:

- Every refusal names what happened **and** the next step. No bare "Not allowed".
- No OAuth error codes in **page** copy, no parameter names, no internal host names, no token,
  code or handle fragments, no trace. (`access_disabled` in R1 is a machine field of a machine
  answer, not page copy.)
- No blame ("you entered"), no apologies ("Sorry!"), no exclamation marks, no emoji.
- The word "password" appears only where it reassures.
- Never "click here". Link text names the destination.
- "Disconnect", never "revoke", in user facing copy. "Revoke" is the word of the specification
  and of the admin documentation; the person reading this page connected an app and wants it
  gone. The two words mean the same operation, and `docs/` keeps using "revoke" where it talks
  to administrators.

## Accessibility Contract

Target WCAG 2.2 AA, unchanged from phase 3. Everything there still applies: one `<h1>` per
page, `<header>`/`<main>`/`<footer>` landmarks, real `<button>` and `<a>`, focus ring
`outline: 3px solid #1F3A5F; outline-offset: 2px` on `:focus-visible` with `outline: none`
forbidden anywhere, 44px minimum interactive size, 200 percent zoom and 320px width without
horizontal scrolling, `color-scheme: light` and no dark mode, no animation.

What this phase adds:

- The connections list is a real `<ul>` with one `<li>` per connection, so a screen reader
  announces how many there are. Not a `<table>`: at 560px a table with an action column
  either scrolls sideways or collapses into something that is no longer a table, and one
  connection has three facts, which is a list item and not a record.
- No heading per row (see Typography). Each row's button carries its own accessible name
  through the app name in it: the visible label is "Disconnect", and the button gets an
  `aria-label` of the form "Disconnect {client}" so that a list of buttons read out of
  context is not five times the same word.
- Each row is its own `<form>`. One form around the whole list with five submit buttons would
  make the keyboard order and the submitted value depend on which button was pressed last,
  which is exactly the ambiguity a destructive action must not have.
- The result callout of S8 is the first thing inside the card, before the section heading, so
  a screen reader that starts at the top hears the outcome first. It is **not** a live region:
  the page was just loaded, and a live region on a freshly loaded page announces twice.
- The confirmation page sets focus to its heading (`focus_heading=True`), the mechanism that
  already exists for the consent screen.
- The client id wraps with `overflow-wrap: anywhere` like every other monospace value.
- Nothing on this surface animates, nothing polls, no meta refresh: the connections page is
  the one browser surface of this project that has no waiting state at all.
